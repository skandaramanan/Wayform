# CEO Plan: Graph Memory Store (SQLite index + embeddings over the git ledger)

Generated by /plan-ceo-review on 2026-07-03
Branch: main | Mode: SCOPE EXPANSION
Repo: skandaramanan/MemoryLayer

## Problem

`read_context` currently returns the last 30 `.md` files in a project directory,
concatenated verbatim (`src/store.ts` `readImpl`, `src/context-format.ts`
`projectContext`). Two failure modes fall directly out of that: (1) context
overhead scales with entry *count*, not tokens, so a run of long entries blows
the budget while short ones waste it; (2) there is no way to tell a superseded
decision from a live one except reading chronologically and inferring it, so
the store degrades into "a pile of MDs" exactly as entries accumulate — the
opposite of what a memory product should do over time.

## Vision

### 10x Check
`read_context(project, budget_tokens, query?)` returns a *ranked, deduped,
graph-expanded* answer to "what does this agent need to know right now,"
not a chronological dump. Old resolved decisions compress into digest nodes
automatically. A decision that supersedes another is linked and the old one
drops out of the default read entirely — no author discipline required to
keep the store honest.

### Platonic Ideal
Git is the durable, vendor-neutral, diffable ledger — that never changes,
it's the moat. Every client (Claude session, Cursor, Codex) rebuilds a local
derived index from the ledger on pull. The index is disposable: delete it,
it rebuilds correctly from git, so there is never a "ledger and index
disagree" bug class. The read path queries the index; the write path appends
to the ledger and updates the index incrementally.

```
CURRENT STATE                       THIS PLAN                              12-MONTH IDEAL
flat .md files per entry   --->    + SQLite index per clone      --->     query-shaped memory:
count-capped concatenation         (nodes/edges/FTS/embeddings)           "what matters now,
no relationships                   auto-classify + auto-supersede         in budget_tokens"
                                    token-budgeted read                    old history -> digests
```

## Architecture

### Storage layers

```
context/<project>/<author>/<ts>-<id>.md   (git, UNCHANGED — source of truth, append-only)
          |
          | rebuilt from git on every pull (disposable, never the source of truth)
          v
.memorylayer/graph.sqlite  (WAL mode; gitignored, lives next to .memorylayer-hook.env)
    nodes(id, project, author, kind, ts, payload, embedding BLOB, resolved BOOL)
    edges(from_id, to_id, kind: supersedes | relates_to | blocks | mentions)
    fts(payload)                              -- FTS5 virtual table over nodes.payload
    meta(last_indexed_sha)                    -- last git commit the index reflects
```

`kind` on nodes: `decision | constraint | question | todo | person-note | digest | unclassified`.
`kind` on edges: `supersedes` (marks source `resolved=true`), `relates_to`,
`blocks`, `mentions` (auto-extracted entity/file/person references).

**Concurrency:** the hook process and the MCP server process are separate
OS processes that can touch the same clone. SQLite WAL mode handles
concurrent readers safely; all *writes* to the index ride the existing
`ContextStore.serialize()` queue (`store.ts:61`) that already serializes
every git-touching op per clone — index upserts are added inside the same
`writeImpl`/`readImpl` critical sections, so no new locking primitive is
needed, only piggybacking on the mutex that already exists.

### Write path (extends `ContextStore.write`)

1. Append `.md` file to git, exactly as today (unchanged, no regression risk).
2. Classify: rule-based only (keyword/structure heuristics — "decided",
   "blocked on", "?" density), producing `kind` + extracted mentions. No LLM
   fallback for ambiguous payloads — that would reintroduce a network call on
   the write path and contradict the "no network dependency" embedding
   promise below. Ambiguous payloads get `kind=unclassified` and are still
   fully indexed/searchable via FTS; classification confidence is not a
   gate on writing.
3. Embed the payload with a small **bundled** local model (quantized
   ONNX, ships inside the npm package — no first-run download, no runtime
   network call; the tradeoff is package size, not network dependency). If
   the embedding step throws (corrupt bundle, unsupported platform), the
   write still succeeds: node is inserted with `embedding=NULL`, and a
   `memorylayer reindex` backfill pass re-embeds it later. Embedding
   failure never blocks or fails a write.
4. Nearest-neighbor search scoped to the last 200 nodes (or 90 days,
   whichever is smaller) in the same project. This is a **non-interactive**
   step — `write_context` is a single synchronous MCP tool call with no
   round-trip for a human yes/no. So: above a high auto-link threshold,
   write the `supersedes` edge automatically and mark the prior node
   `resolved=true`; between the auto-link threshold and a lower
   surface-only threshold, do NOT auto-link — instead return
   `related: [{id, similarity, ts}]` in the tool's response payload so the
   calling agent/human can see it and issue an explicit follow-up write
   with `supersedes: <id>` if they agree. No blocking prompt exists anywhere
   in this pipeline.
5. Upsert node + edges into the SQLite index.

### Pull-triggered indexing (entries from other authors' clones)

Every read and write already calls `this.repo.pull()` first (`store.ts:92`,
`148`). After a pull, diff the working tree against the index's last-seen
git commit SHA (stored as a single row in the index) and run steps 2-3-5
above (classify, embed, upsert) for every `.md` file that's new since that
SHA — auto-link only (no `related` surfacing, since there's no synchronous
caller to hand it to); anything below the auto-link threshold stays
unlinked until a human write touches it. This is the same "index is
disposable, rebuilds from git" property applied incrementally instead of
from scratch.

### Read path (replaces `read()`'s count cap)

`read_context(project, budget_tokens, query?)`:
1. If `query` given: embed it, pull nearest-neighbor candidates. If not:
   default to "everything unresolved + recently touched."
2. Graph-expand one hop (pull in `relates_to`/`blocks` neighbors of
   candidates) so a returned decision brings its live constraints with it.
   **Expansion excludes `resolved=true` nodes** — a superseded node never
   re-enters the response as someone else's neighbor; it only surfaces
   inside its digest (or on an explicit history query, see Compaction).
   This is what actually enforces the Vision's "superseded decisions drop
   out of the default read entirely," not just the ranking step below.
3. Rank: unresolved > recency > similarity.
4. Greedily pack nodes into `budget_tokens`, digest nodes counting for their
   compressed size, not their underlying raw-node size.
5. Render via a new `graphContext()` projection (replaces flat
   `projectContext()` concatenation) — same MCP/hook surface, structured
   output. The hook path (`hook.ts`, `stop-hook.ts`) calls this with a
   default `budget_tokens=4000` (configurable via `.memorylayer-hook.env`,
   same convention as existing hook config), matching roughly the old
   30-entry cap's typical size but bounded by tokens instead of count.

### Compaction (background, not on the write/read hot path)

Nodes that are `resolved=true` and older than N days (config, default 30)
roll up into a single `digest` node per project via periodic job (cron-like,
runs on `flushMetrics`-style piggyback or a separate `memorylayer compact`
command — no new daemon). Raw nodes stay in git forever (ledger is
immutable) and stay queryable on demand ("show me the history behind this
digest"), they just drop out of the *default* read path. This is what lets
the ledger grow unbounded without `read_context` ever growing.

### Migration

Additive only. Existing `.md` files are re-indexed once on first run of the
new binary (walk `context/`, classify + embed + insert — same collectMarkdown
walk that `readImpl` already does). No git history rewrite, no format change
to the ledger. `ContextStore.read()`'s old count-capped path can stay as a
fallback if the index is missing/corrupt (self-healing, matches the existing
`selfHealPush` philosophy of "never block on the fancy path").

## Accepted Scope (added to this plan)
- SQLite derived index: nodes, edges, FTS5, embeddings — rebuilt from git, never the source of truth
- Typed node classification (decision/constraint/question/todo/person-note/digest) + auto mention extraction
- Auto contradiction/supersession detection with writer confirmation prompt
- Token-budgeted, graph-expanded, ranked `read_context` replacing the count-capped concatenation
- Background compaction of resolved/old nodes into digest nodes
- One-time re-index migration of existing `.md` entries, additive only

## Open Questions for Implementation (temporal interrogation)
- Embedding model choice: local (no network dependency, keeps vendor-neutral promise) vs. API call (simpler, but reintroduces a dependency + cost per write). Recommend local for the write path; decide before Hour 1.
- Similarity threshold for supersession prompts: too low = annoying false positives on every write; too high = misses real conflicts. Needs a tunable default + override flag, decide before building #5.
- Where does `.memorylayer/graph.sqlite` live relative to the existing `.memorylayer-hook.env` / repoPath convention — same repo clone dir, gitignored. Confirm before Hour 1 so paths aren't improvised mid-build.
- Digest node format: does a digest still carry enough detail to answer "why did we decide X" or is it lossy summary only with a pointer back to raw nodes? Decide before building #6 — this is the difference between compaction and data loss.

## Dependency & Packaging Risk

Today `package.json` has zero native dependencies (`@modelcontextprotocol/sdk`,
`simple-git`, `zod` — all pure JS). This plan adds:
- A SQLite driver (e.g. `better-sqlite3`) — a native module requiring
  compilation, which is a real new cross-platform build/CI risk (node-gyp,
  prebuilt-binary availability per OS/arch) for a package that ships as a
  thin `bin: dist/cli.js` CLI today.
- A bundled local embedding model — increases package size (tens of MB)
  and is new packaging surface (asset bundling, not just TS compilation).

Both are legitimate, known tradeoffs of going local-first/vendor-neutral
instead of calling an external embedding API — flagging explicitly so
they're a conscious choice, not a surprise mid-build.
